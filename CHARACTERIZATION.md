## Inference and pooling

ONNX Runtime C exposed three `int64` inputs `[1, N]`: `input_ids`, `attention_mask`, and `token_type_ids`; the observed `last_hidden_state` output was `float32` `[1, N, 384]`. Three texts with all-one masks and no padding produced different means; pairwise cosines were approximately 0.104921, 0.293307 and 0.107481. Unnormalized mean norms were 4.928309, 5.099980 and 5.533683.

The Tcl extension returned normalized means with maximum absolute difference `5.56e-17` against a C calculation for those three cases. `tests/tokenizer_embedding_test.tcl` checks IDs, dimension, norm, three components per vector and distinct vectors. The original complete C comparison program is not retained here, so the historical figure cannot be fully reproduced from that test alone. There was no comparison with a complete independent Sentence Transformers implementation or padding masks. Token parity does not prove embedding parity.

The locally available `modules.json` declares Transformer and mean Pooling only, with no Normalize module. The tokenizer JSON specifies longest-first truncation at 128 and right `BatchLongest` padding, while `tokenizer_config.json` reports `model_max_length` 512. `config.json` declares 512 positions and hidden size 384. The local artifact set does not contain `sentence_bert_config.json` or PyTorch weights. The [official configuration at the exact revision](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2/raw/e8f8c211226b894fcb81acc59f3b34ba3efd5f42/sentence_bert_config.json) specifies `max_seq_length: 128` and `do_lower_case: false`; the later VM reference reports an effective default of 128, as recorded in 003-B2 below. The locally inspected `modules.json` and `1_Pooling/config.json` have the hashes identified above and specify Transformer plus mean Pooling at dimension 384, without Normalize. Their hashes also match the transferred VM manifest.

For a single input, the tokenizer template adds `<s>` ID 0 and `</s>` ID 2; `<pad>` is 1, `<unk>` 3 and `<mask>` 250001. The model configuration instead specifies `pad_token_id` 0. The practical effect of that discrepancy has not been characterized. The Tcl tokenizer disables stored truncation and padding by default and applies an explicit `-max-length` without enabling padding. The ONNX C API reported three dynamic-rank-2 `int64` inputs `input_ids`, `attention_mask`, `token_type_ids`, and a dynamic `float32` output `last_hidden_state` of shape `[batch, sequence, 384]`. This observation does not independently identify the precision of every model weight.

The binding builds a batch of one, uses the provided IDs, an all-one attention mask and all-zero type IDs, averages token positions in double precision and applies L2 normalization with a `1e-9` minimum denominator. It cannot accept arbitrary masks or padding. At the time of 003-A, a raw empty ID list returned an empty list; 003-B1 subsequently changed this to an error. Tokenizing an empty string with special tokens yields two IDs and a 384-component vector. No true zero-norm model output was produced in 003-A; the subsequent synthetic test and zero-norm rejection are described below.

## Slice 003-B1 — native input and output safety

Slice 003-B1 was formally accepted with the limitations below; Slice 003 as a whole was accepted subsequently, limited to the evaluated evidence.

`embedding::compute` now rejects empty lists and IDs that are not nonnegative signed 64-bit integers. It checks the exact Tcl integer before converting to `Tcl_WideInt`: in this environment `Tcl_GetWideIntFromObj` alone wrapped some out-of-range negative values into positive values. It also checks allocation and output-index size products. No upper vocabulary bound was added.

Before reading output data, the binding checks that ONNX returned a tensor, checks `float32`, rank 3, dimensions `[1, token_count, 384]` and element count, and handles API errors. Zero norm or non-finite means and norms return Tcl errors. Finite nonzero inputs retain the existing order of operations and `1e-9` minimum denominator. No inference, pooling, default truncation or padding policy was changed.

Code inspection confirms that a null output is rejected and `IsTensor` is checked before `GetTensorMutableData` or any output-data access (`generic/tclembedding.c`). These checks are implemented; the null-output and non-tensor branches have not been exercised experimentally.

On the environment and exact MiniLM artifacts above, the 18-case Tcl/C-to-ONNX comparison passed before and after; complete Tcl ID/vector output matched byte for byte with SHA-256 `a65c2d08c270e05eae1ef27a2f0ef304d82d8292c12cca57293f436a41985e35`. The independent C client uses the same ONNX Runtime, so this remains binding consistency evidence, not PyTorch parity. The Slice 002 three-vector tolerance and lifecycle tests, and the three text-to-ONNX integration cases, passed. A generated tiny nonzero-norm model also produced identical serialized output before and after, retaining the existing clamp behavior.

`tests/make_onnx_safety_fixtures.py` creates small synthetic ONNX files without external packages. `tests/embedding_safety_test.tcl` passed cases for empty, noninteger, negative and out-of-range IDs, including negative wraparound, and recovery on the same handle; it also accepted the maximum signed 64-bit ID with a synthetic constant-output model. Synthetic outputs exercised rank, batch, sequence and hidden-size mismatches, int64 instead of float32, zero, NaN and infinity. Errors were recoverable; a 522-token real-model input returned an ONNX error and the same handle subsequently produced a 384-component vector. Tests did not force a null or non-tensor ONNX output, inconsistent runtime-reported element count, arithmetic overflow, individual runtime API failures, or every non-finite pattern. Those paths must not be assumed experimentally covered.

Valgrind 3.27.1 ran with `--vgdb=no --leak-check=full --show-leak-kinds=definite,indirect,possible --errors-for-leak-kinds=definite,indirect --error-exitcode=42`. A Tcl package baseline, a synthetic successful session/inference/free, and a successful MiniLM session/inference/free all exited 0, reported no invalid-access errors and had zero definitely and indirectly lost bytes. The baseline reported 1,464,320 possibly lost bytes in 84 blocks; the synthetic and MiniLM runs each reported 1,431,552 bytes in 82 blocks. Respective reachable totals were 201,733, 219,237 and 235,621 bytes. Inspected possible-loss traces include Tcl allocator frames; they do not establish a cause. This bounded instrumented run satisfies the previously recorded request to instrument a successfully loaded ONNX session, but does not prove general leak freedom or characterize concurrency and other error paths.

The same Valgrind options were also applied to the synthetic safety test, including invalid IDs and output error paths. It passed with zero reported errors and zero definitely or indirectly lost bytes; 1,371,136 bytes in 81 blocks were possibly lost and 296,037 bytes remained reachable. Possible losses were not counted as errors by these options. The binding now uses Tcl's bundled TomMath integer API for exact range validation; builds using other Tcl configurations or platforms remain unverified.

The comparison has complete final hidden tensors, but not per-layer activations or each model's exported weights in this environment, so backend, export, weight and hardware contributions to the nonzero hidden-state difference cannot be separately attributed. The binding does not expose its own raw hidden tensor or unnormalized pooled intermediate; the separate C client supplies those ONNX stages, and the final Tcl/C equality is observed. Results do not establish parity for other revisions, masks, padding, batch sizes, inputs, devices or runtimes. No new model, normalization, truncation or padding policy is approved by these observations.

## Slice 004-A — build and installation audit

Slice 004, including 004-A and 004-B1 through 004-B3, was formally accepted within the evaluated Linux x86-64 environment and the identified, previously available external dependencies. This does not establish binary reproducibility, reconstruction from the then-current `HEAD` alone, self-contained distribution or compatibility with other platforms. The stage-specific evidence and limits follow.

This audit described the working tree at the time, including previously untracked files, not a clean checkout of `HEAD`. The inspected commit was `b333cd3f44d2a0d7d5bfe888c634d7f812ad3794`; `tokenizer-native/` and `generic/tokenizer_bridge.c` were untracked in the audited tree and are absent from that commit. Consequently, the then-existing `git archive ... HEAD` instructions would not include the Rust backend or its bridge. No staging or commit was performed.

At the time of the audit, the repository contained `configure.ac`, `autogen.sh`, root and Unix makefile templates and `pkgIndex.tcl.in`, but no `tcl.m4`, `aclocal.m4`, generated `configure` or `install-sh`. In an isolated copy containing the configuration and makefile templates, `autogen.sh` returned success and generated `configure`; the unmodified configuration then failed because `install-sh` was missing. With a temporary failing placeholder supplied only to move past that check, and the system C compiler selected explicitly, `configure` failed at the unexpanded `TEA_INIT(3.13)` token. The initial `autogen.sh` warning about missing Tcl development files resulted from its default `pkg-config` search; Tcl 8.6.14 and a usable `tcl.pc` were present outside that default search path. The subsequent 004-B1 configuration changes are documented below.

In a separate isolated build directory, the Unix template was invoked directly with explicit source path, compiler, Tcl include/link flags and ONNX Runtime flags. The C binding and bridge were compiled from the working-tree sources. Rust was built with `--locked`, network access disabled, a fresh Cargo target directory and an existing cache of crate sources; no previously compiled tokenizer library was used. ## Native dependency evaluation

### Token details and byte offsets

The additive tokenizer details path calls Tokenizers 0.23.2 `encode` once and returns the resulting IDs, byte offsets, special-token mask, attention mask and type IDs. The public Tcl record order is documented in `README.md`. Offsets are into the exact standard UTF-8 byte sequence given to Rust; end offsets are exclusive. The binding does not convert them into Tcl indices and does not establish grapheme boundaries. For the identified MiniLM tokenizer, `café 😀` produced offsets `(0,0), (0,5), (6,10), (0,0)` in bytes; `encode_char_offsets` produced `(0,0), (0,4), (5,6), (0,0)` with identical IDs. The corresponding byte and character APIs were compared on that input for the other three hash-identified models as well.

For MiniLM, the literal `<s>` retained ID 0 with mask 0 and source range `(0,3)`, while the inserted ID 0 had mask 1 and `(0,0)`. The four identified tokenizers were checked with literal specials, empty text, NFC/NFD, combining marks, supplementary emoji, ZWJ, modifiers, CJK, spaces, embedded NUL, unknowns and explicit truncation. A valid special ID is not necessarily identified as special by the postprocessor mask. Offset ranges must not be assumed contiguous or disjoint, and normalizers can remove or transform source characters.

The C ABI owns a newly allocated array of fixed-width records; its paired release function resets the caller's pointer and count slots and can be repeated on those same slots. Copied aliases, invalid pointers, stale slot values and concurrent destruction are outside the contract. The current package version remains 1.0.0 for exact-version compatibility; consumers should detect the new command explicitly. This is a limited characterization, not a claim of generic tokenizer, Unicode or thread safety.

Native token offsets and masks were subsequently accepted within the characterized scope. The complete suite passed after the final Rust test change with Tokenizers 0.23.2 and ONNX Runtime 1.31.1; 11 Rust tests and the existing C/Tcl and ONNX checks passed. ### Slice 008 — focused technical review

A synthetic ONNX graph declared hidden dimension 2 but returned dimension 8,193 at runtime. ONNX Runtime 1.20.1 warned about the discrepancy, and the original batch implementation accepted the output: the pre-run metadata check alone did not enforce the bound on the actual tensor. The batch path now requires the actual hidden dimension to equal the validated static metadata and rechecks the actual bounds before allocating the pooled vector or accessing output data. Synthetic fixtures exercise both a 2-to-3 mismatch and the 2-to-8,193 mismatch, with controlled errors. This does not prevent ONNX Runtime itself from allocating its output or other internal tensors before returning it. The existing `embedding::compute` path was not changed and still validates its effective output dimension without requiring a static declaration.

The three-row synthetic fixtures use exactly representable integer-to-float casts and compare expected normalized values with absolute tolerance `1e-12`, avoiding byte-for-byte Tcl formatting comparisons. Real-model exact matches remain observations of the measured environment. Exhaustive injected allocation failures and arbitrary malformed ONNX Runtime responses remain untested.
